09) Contas reais (port/server/contas.py) — ADAPTAÇÃO DOCUMENTADA:
    O acervo espera do servidor apenas os parsers 326/327; o que está por
    trás deles é nosso. Contrato mantido:
    - pedido 9001: usuario \r\n senha \r\n confirmacao \r\n <PackageName>
      (AccountSysRegister.lua:64-74) -> 326 com o nome da conta.
    - pedido 9002: usuario \r\n segredo \r\n <PackageName>
      (AccountSysManager.lua:150-161); segredo = senha em texto OU
      "@tk1:<token>" quando o cliente reusa a sessão lembrada
      (account_sys_login_secret, AccountSysManager.lua:60-70) -> 327.
    - 327 devolve: m_sUin, userLoginToken, userLoginPackageName,
      userAccountCreateTime (ProtocolParser.lua:1193-1208).
    Regras de armazenamento (nossas, não inventadas no protocolo):
    - SQLite em port/dados/contas.sqlite3 (fora dos recursos originais).
    - senha: PBKDF2-HMAC-SHA256, salt de 16 bytes por conta, 200000
      iterações, formato "pbkdf2_sha256$iter$salt_b64$hash_b64".
      Nunca texto puro, nunca reversível.
    - token de sessão: 32 bytes de os.urandom em base64url = 43 chars, que
      é exatamente o formato exigido por account_sys_valid_token
      (AccountSysManager.lua:38-41). Sessões ficam na tabela sessoes e são
      revogadas no logout.
    - unicidade do nome: normalizado para minúsculas e sem espaços nas
      pontas (a coluna `nome` é UNIQUE); o nome exibido é o digitado.
    - validação: nome 3..20 [A-Za-z0-9_.-]; senha 6..32 sem espaço/|/CR/LF
      (quebram o protocolo, que separa campos por CRLF).
    - recusa de conta: status -1 + mensagem (NetworkProtocol.lua:184 abre a
      caixa de erro do cliente). Comandos fora da lista SEM_OPERACAO (item 2)
      respondem status -3 "nao_implementado", nunca sucesso genérico.
    - vali_register e login_init exigem SESSÃO da própria conta (item 09).
      Conta desconhecida, sessão ausente, inválida, expirada ou revogada ->
      status -1. Existir no banco não basta.
    - perfil: tabela perfis (conta_id -> user_id, user_name), criado na
      primeira entrada; user_id/user_name do login_init vêm dele, então
      contas diferentes ficam isoladas.

10) VÍNCULO SESSÃO / CONTA / PERFIL (prioridade 2) — ADAPTAÇÃO DOCUMENTADA:
    A identidade de CADA pedido vem do próprio pedido, aproveitando campos
    que o acervo JÁ envia (nenhum campo novo inventado no protocolo):
    - command_login_init (ProtocolCommanderCopy.lua:100-129) manda, nesta
      ordem, no corpo: versão, idioma, param_list, userLoginPackageName,
      userLoginToken, getPlatformParam(), m_sUin, m_sSessionId.
      userLoginToken é global preenchida pelo parser 327
      (ProtocolParser.lua:1197), então o token da sessão viaja em todo
      login_init seguinte.
    - vali_register manda platform_account no corpo (login.lua:706/708/745).
    O servidor procura a conta e o token nesses campos
    (_identidade_do_pedido) e valida com Banco.sessao_de(token, conta):
      * token inválido/desconhecido/sintaticamente errado -> sessao_invalida
      * token vencido -> sessao_expirada (a linha é apagada)
      * token de OUTRA conta -> sessao_de_outra_conta
    Regra de ouro: uma conta NUNCA recebe o perfil de outra.
    Fallback de conexão (_sessao_da_conexao): só quando o pedido não traz
    token — o C2S 3 (search_user_platform) não leva credencial nenhuma. É a
    última 327 emitida por esta instância local e é SEMPRE revalidada no
    banco (token revogado/expirado deixa de valer). O antigo
    _token_lembrado global, que atravessava contas, foi removido.
    - Rotação: login com "@tk1:<token>" revoga a sessão antiga e emite uma
      nova, então um token vazado não vale para sempre.
    - Logout: o acervo não tem comando HTTP de logout (LOGOUT é mensagem de
      SDK, ThirdpartySupporter.lua:23). O adaptador cliente manda
      local_logout (C2S 990001, extensão declarada aqui), que revoga a
      sessão e limpa m_sUin/userLoginToken/_ED.user_platform no cliente.
    - Log: nunca imprime senha nem token completo (só 3 chars + tamanho).
    - Banco existente é preservado: nenhuma migração destrutiva; as tabelas
      são criadas com IF NOT EXISTS e contas/perfis já gravados ficam como
      estão.

11) get_system_notice (C2S 66 -> parser 999, ProtocolParserCopyEx.lua:4-7):
    O parser lê UM campo, a string do anúncio (_ED.system_notice_ex). O
    formato de item do acervo está em AnnouncePage.lua:166. Limite medido:
    o cliente abre a AnnouncePage por a resposta ter voltado
    (RESPONSE_SUCCESS = HTTP 200, NetworkAdaptor.lua:596), NÃO pelo status
    nem pelo conteúdo — qualquer resposta abre a janela; vazio abriria uma
    janela VAZIA sobre o login. Por isso o servidor devolve um anúncio real
    e curto (texto do modo local, não é dado de jogo) e o ACK genérico não
    é usado aqui. Não inventa gameplay: é só um aviso de texto.
